potatOS 运行图解

potatOS 是一个用 Go 编写的 agent core SDK，用于在你自己的程序中构建能够调用工具、多轮工作的 agent。本页说明 agent 收到一条消息之后，这条消息在 potatOS 中按什么顺序经过哪些部件，以及你可以在哪些位置介入。内容从最外层的模块分层开始，逐步深入到一次 turn 中的每一个步骤。

对应 spec 版本 0.4 · 事件序列取自一次真实运行
01

基本术语

代码、事件和文档中反复使用以下五个术语，它们按所指的范围从大到小排列。本页后面的所有图解都以这些术语为基础。

session
一段对话，包含对话历史、正在运行的任务和事件订阅者。一个 session 同一时刻最多运行一个 turn，一个 Agent 可以开启多个 session。
turn
从一批输入送达开始，到模型给出最终回答为止的过程。turn 也可能因中断、达到上限等原因提前停止。
step
一次模型调用及其引出的工具执行。一个 turn 由若干个 step 组成，默认不限个数，可以用 Limits.MaxSteps 设置上限。
attempt
同一个 step 中对模型的一次调用尝试。失败的 attempt 不会写入历史，因此重试是安全的。
epoch
两次压缩或 /clear 之间的一段历史。system 提示词和工具定义在一个 epoch 内保持冻结，使 prompt 缓存持续有效。
02

模块分层与 kernel 的职责

kernel 本身只负责调用模型、运行事件循环和管理上下文这三件事。subagent、skills、memory、A2A 以及各个斜杠命令都以扩展包的形式实现。这些扩展只使用公开的注册接口，与你自己编写的扩展没有区别。

  • 删除一个包即可下线对应的功能。删除任意一个 ext/<x> 包以及 std/std.go 中对应的一行之后，kernel 不需要做任何修改。internal/archtest 中的测试会检查这一点以及各层的依赖方向。
  • 只依赖标准库，唯一的例外是 ext/mcp。ext/mcp 使用官方 MCP Go SDK 以及 golang.org/x/oauth2 和 jsonschema-go，internal/archtest 只允许这个包 import 它们。tools/schemacheck 是独立的 module，校验 schema 用的库不会进入 SDK 的依赖。
  • provider 层可以单独使用。三个适配器都不依赖 kernel，因此可以作为独立的库使用，把三家 API 的流式响应统一成同一种格式。
03

Session 内部的 actor 与 worker

每个 session 都有一个 actor goroutine，会话状态只由它持有。actor 自身从不等待网络，也不运行用户代码，因此 Send、Interrupt 等方法总是立即返回。调用模型、执行工具、运行 hook 和运行任务这类耗时操作都交给 worker goroutine 完成。worker 需要读写会话状态时，会把一个闭包交给 actor 执行。

  • 历史令牌。任一时刻只有一个 worker 能够修改历史和调用 store，这个 worker 可能是正在运行的 turn，也可能是 /compact、/clear 这类命令。因此 store 调用天然是串行的，不需要加锁。
  • Session 的状态。Session 创建后处于 initializing 状态，之后进入 idle，并在 idle 与 running 或 maintenance 之间来回切换。关闭时依次进入 closing 和 closed。初始化期间到达的输入会先排队，不会丢失。

06

工具、审查与任务

审查闸门的判定顺序

  • kernel 按调用顺序先运行 pre_tool_use hook，再基于改写后的输入求值审查规则。pre_tool_use hook 可以改写输入、直接拒绝调用，或者给出一个合成结果。
  • 在规则之间，deny 的优先级最高，显式的 allow 可以豁免 ask，没有命中任何规则时放行。在 hook 与规则之间，以更严格的一方为准。只要任何一方要求 ask，另一方的 allow 就无法豁免。
  • 命中 ask 的调用会并发触发 approval hook。该 hook 默认没有超时，一定会等到审查者给出回答。整批调用都有结论之后才开始执行。如果没有注册审查者，ask 一律按拒绝处理。
  • 子 agent 和后台任务中的工具调用同样交给这套规则和审查者处理，不会绕过审查。

工具的执行

  • 连续的 Parallel 调用合并为一组并行执行，每个 Serial 调用单独成为一组，组与组之间串行执行。因此，只读工具适合声明为 Parallel 以并行执行，有副作用的工具适合声明为 Serial，以保持模型给出的顺序。
  • 执行结果按调用顺序写入同一条 tool 行。发生中断时，每个调用都会补上结果，因此历史不会损坏。
  • 对于声明了 Background 的工具，模型可以传入 background:true 将其转为后台任务，此时这次调用会立即返回一个 task_id。

任务与结果通知

任务是一种异步执行的能力，例如 subagent、A2A 和你自己编写的 workflow。任务启动后立即返回。当任务结束、失败或需要输入时，kernel 会主动把通知放入输入队列，因此模型不需要轮询任务状态。

子 agent 默认跟随父会话的模型。宿主可以在 subagent.Options 里用 Models、Efforts 和 ResolveModel 声明可选值；声明之后，模型调用 subagent 工具时才能选 model 和 effort，也就是模型和强度。某个类型也可以在定义里用 FixedModel 固定模型：写了具体模型就用它，没写就跟随父会话，这时调用里选的值会被忽略。subagent_start hook 能看到并改写这两个选择。

07

上下文与存储

system 提示词的固定结构

system 提示词各段的顺序由 kernel 决定。扩展只能向其中三个开放的槽位写入内容，用户段只能通过 WithInstructions、WithInstructionsFunc 或 SessionInstructions 写入。整个 system 提示词在一个 epoch 内保持冻结，时间、任务通知这类动态内容会以 reminder 的形式追加到 user 侧的消息中。

  1. 1core运行约定，说明 reminder、任务通知和其他 agent 来信的含义，所有 agent 都相同
  2. 2identity昵称与描述，通过 WithNickname 和 WithDescription 设置
  3. 3capabilities扩展的使用说明，写入 SlotCapabilities 槽位
  4. 4user你的指令，可以用 WithInstructions 等三种方式写入，优先级高于上面的能力说明
  5. 5catalog目录，列出可用的 skills 和可调用的 agent，写入 SlotCatalog 槽位
  6. 6environment环境事实，写入 SlotEnvironment 槽位

上下文窗口不一定由模型决定。创建或恢复会话时可以传 kernel.SessionContextWindow(n)，运行中可以用 Session.SetContextWindow(n) 修改：给了具体值就以它为准，可以比模型自报的窗口更大；传 0 表示继续跟随模型。修改从下一次模型调用起生效，Context() 会立刻反映新值；窗口会写进会话文件，Resume 时自动恢复，fork 也沿用源会话的窗口。自动压缩的阈值按这个有效窗口计算。

以 JSONL 存储的会话文件

  • message 的 JSON schema 就是存储格式。Go 版本写下的会话可以由其他语言版本直接恢复。如果改用数据库存储，每一行对应一条记录。
  • 上下文管理的接口都由 kernel 提供。这些接口包括 Compact、Clear、Rewind、Fork、SideChat、SearchHistory、Context、SetContextWindow、Unpin，对应的斜杠命令位于 ext/cmd/*。Rewind 和 ForkAt 既可以传轮次 id，也可以传输入 id；按输入截断时，同一行里合并的几条输入会一起丢弃。
08

kernel 提供的运行保证

  • 工具不会重复执行回复先写入历史，然后才执行工具，失败时只重试模型调用。执行前 kernel 还会按 call_id 查询账本。
  • 历史始终合法无论是中断、出错还是被 hook 阻断，finish 都会为每个悬空的 tool_call 补上结果。
  • 请求不会以 assistant 消息结尾唯一的例外是 Anthropic 的 pause_turn 续写。
  • 公开方法不阻塞调用方Send、Interrupt 和 Snapshot 都会立即返回。如果需要等待结果，请使用 Receipt.Wait。
  • 事件有序，默认不丢失订阅者处理得慢时只会让模型流等待。子 agent 发出的事件带有 Path，可以据此判断事件来自哪个 agent。
  • 非人类输入不视为授权reminder、任务通知和其他 agent 的来信都带标签送达，system 提示词的 core 段会告诉模型这些内容不是用户说的话。
