potatOS Runtime, Illustrated

potatOS is an agent core SDK written in Go. You use it to build agents inside your own program that can call tools and work over multiple turns. This page shows what happens after an agent receives a message: which parts of potatOS the message passes through, in what order, and where you can step in. It starts with the outermost layering of the modules and works its way down to every step of a single turn.

01

Basic terms

The following five terms appear throughout the code, the events and the documentation. They are listed from the broadest scope to the narrowest, and every diagram on this page builds on them.

session
A conversation, including its history, its running tasks and its event subscribers. A session runs at most one turn at a time, and one Agent can open many sessions.
turn
The process that starts when a batch of input is delivered and ends when the model gives its final answer. A turn can also stop early, for example because it is interrupted or reaches a limit.
step
One model call plus the tool executions it leads to. A turn consists of several steps. The number of steps is unlimited by default, and you can set a limit with Limits.MaxSteps.
attempt
One try at calling the model within a step. A failed attempt is never written to history, so retrying is safe.
epoch
The stretch of history between two compactions or /clear commands. The system prompt and the tool definitions stay frozen within an epoch, which keeps the prompt cache valid.
02

Module layers and the kernel's responsibilities

The kernel itself is responsible for only three things: calling the model, running the event loop and managing context. Subagents, skills, memory, A2A and the slash commands are all implemented as extension packages. These extensions use only the public registration interfaces, so they are no different from extensions you write yourself.

  • Deleting a package is enough to remove its feature. After you delete any ext/<x> package and its line in std/std.go, the kernel needs no changes. Tests in internal/archtest check this, as well as the direction of the dependencies between layers.
  • Standard library only, with ext/mcp as the one exception. ext/mcp uses the official MCP Go SDK together with golang.org/x/oauth2 and jsonschema-go, and internal/archtest allows only that package to import them. tools/schemacheck is a separate module, so the library it uses to validate schemas never becomes a dependency of the SDK.
  • The provider layer can be used on its own. None of the three adapters depends on the kernel, so you can use them as a standalone library that turns the streaming responses of all three APIs into one common format.
03

Actors and workers inside a session

Every session has one actor goroutine, and only the actor holds the session state. The actor itself never waits on the network and never runs user code, so methods such as Send and Interrupt always return immediately. Slow work such as calling the model, running tools, running hooks and running tasks is handed to worker goroutines. When a worker needs to read or write the session state, it hands a closure to the actor to run.

  • The history token. At any moment only one worker can modify the history and call the store. That worker is either the running turn or a command such as /compact or /clear. Store calls are therefore serialized by design and need no locking.
  • Session states. A session starts in the initializing state, then enters idle, and from there moves back and forth between idle and either running or maintenance. When it closes, it passes through closing and then closed. Input that arrives during initialization is queued, not lost.

When new input reaches a running agent

06

Tools, approval and tasks

How the approval gate decides

  • The kernel first runs the pre_tool_use hooks in call order, then evaluates the approval rules against the rewritten input. A pre_tool_use hook can rewrite the input, deny the call outright or supply a synthetic result.
  • Among the rules, deny takes the highest priority, an explicit allow can exempt a call from ask, and a call that matches no rule is allowed. Between hooks and rules, the stricter side wins: as soon as either side requires ask, an allow from the other side cannot exempt the call.
  • Calls that hit ask trigger the approval hook concurrently. By default this hook has no timeout and always waits until the approver answers. Execution starts only after every call in the batch has a decision. If no approver is registered, every ask is treated as a denial.
  • Tool calls made inside subagents and background tasks go through the same rules and approvers, so they never bypass approval.

Running tools

  • Consecutive Parallel calls are merged into one group that runs concurrently, each Serial call forms a group of its own, and the groups run one after another. Read-only tools are therefore a good fit for Parallel, so that they run concurrently, and tools with side effects are a good fit for Serial, which keeps the order the model gave.
  • The results are written to a single tool row in call order. If an interrupt happens, every call still gets a result, so the history is never corrupted.
  • For a tool that declares Background, the model can pass background:true to turn the call into a background task. The call then returns a task_id immediately.

Tasks and result notifications

A task is a capability that runs asynchronously, such as a subagent, an A2A call or a workflow you write yourself. Starting a task returns immediately. When a task finishes, fails or needs input, the kernel puts a notification into the input queue on its own, so the model never needs to poll for the task's status.

07

Context and storage

The fixed structure of the system prompt

The kernel decides the order of the sections in the system prompt. Extensions can write only into three open slots, and the user section can be written only through WithInstructions, WithInstructionsFunc or SessionInstructions. The whole system prompt stays frozen within an epoch, and dynamic content such as the current time or task notifications is appended to user-side messages as reminders.

  1. 1coreRuntime conventions that explain what reminders, task notifications and messages from other agents mean. This section is the same for every agent.
  2. 2identityThe nickname and description, set with WithNickname and WithDescription
  3. 3capabilitiesUsage notes for extensions, written into the SlotCapabilities slot
  4. 4userYour instructions, written in one of three ways such as WithInstructions. They take priority over the capability notes above.
  5. 5catalogA catalog of the available skills and the agents you can call, written into the SlotCatalog slot
  6. 6environmentFacts about the environment, written into the SlotEnvironment slot

Session files stored as JSONL

  • The message JSON schema is the storage format. A session written by the Go binding can be resumed directly by a binding in another language. If you store sessions in a database instead, each line becomes one record.
  • The kernel provides all the context management interfaces. These are Compact, Clear, Rewind, Fork, SideChat, SearchHistory, Context and Unpin, and the matching slash commands live in ext/cmd/*.
08

Runtime guarantees from the kernel

  • Tools never run twiceThe reply is written to history before any tool runs, and after a failure only the model call is retried. Before running a call, the kernel also checks the ledger by call_id.
  • History is always validWhether the turn is interrupted, fails or is blocked by a hook, finish fills in a result for every dangling tool_call.
  • Requests never end with an assistant messageThe only exception is Anthropic's pause_turn continuation.
  • Public methods never block the callerSend, Interrupt and Snapshot all return immediately. If you need to wait for a result, use Receipt.Wait.
  • Events are ordered and, by default, never lostA slow subscriber only makes the model stream wait. Events from a subagent carry a Path, which tells you which agent they came from.
  • Non-human input never counts as authorizationReminders, task notifications and messages from other agents are delivered with tags, and the core section of the system prompt tells the model that this content is not something the user said.
