# ext/memory

Instruction files and the long-term memory of a user and project, written into the head of every new epoch and followed like standing instructions; the model changes the memory with tools, and a consolidation keeps it small when a session ends or compacts. The tool definitions are `tools.json`; every other text the model sees is a section of `texts.md`, rendered by the template language of `runtime.md` §7.

- **Tags and scope.** A memory has a `user` and a `project` tag, each empty or one value. A session's scope is its user and project, by default its labels `user_id` and `project_id`; it sees every memory whose two tags are each empty or the scope's. A change may set a tag only to the scope's value or empty.
- **Loading.** A `session_start` hook named `memory`, for sources `new`, `clear` and `compact` only (a resume keeps its epoch head, and a fork or rewind copies one), answers as its context, joined by blank lines: one `instruction_doc` per instruction document, then, when there is a store, `loaded` with `{{memories}}` one `memory` line per memory the scope sees, oldest first, its content's whitespace runs as single spaces, or `empty` when there is none. The runtime writes it into the epoch head as a reminder with source `hook:memory`. With a store it publishes `memory.loaded{ids}`. The file source reads the named files in order, skips missing and empty ones, trims each, and stops at 25600 bytes in all: the file that crosses the limit keeps what fits, ending before an incomplete code point, followed on the next line by `instructions_truncated` with `{{limit}}` 25600.
- **Checking a batch.** A batch of changes (`add` with content and tags, `update` of an id with any of content and tags, `delete` of an id) is checked against the memories the scope sees, in order: a tag other than the scope's value or empty fails with `bad_tag`, an unknown id with `no_memory`, an empty content with `need_content`. The memories with a user tag and the others then each have to fit their limit (`user_tokens` and `shared_tokens`, 10000 each by default), counted by the runtime's text heuristic (`runtime.md` §12.1); otherwise it fails with `over_limit`. A batch that fails changes nothing; one that passes is applied at once and published as `memory.saved{changes, trigger}`, the added changes carrying their new ids.
- **Own memories only.** Unless `shared_writes` is set, a batch from the model (the tools and a consolidation) stays under the scope's user when the scope has one, before it is checked: an `add` whose user tag is absent or empty takes the scope's user, an `update` that would empty the user tag keeps the scope's user, and an `update` or `delete` of a memory whose user tag is not the scope's user is refused, from a tool with `shared_read_only` (`{{id}}` the memory), from a consolidation by leaving that change out. A memory every user shares steers every user's sessions, so one injected instruction must not plant or remove it. A store that implements the ingester interface decides for itself.
- **Tools** (with a store, unless turned off; serial). `memory_save` is an `add`, or with `replaces` an `update` of that id with the content and both tags: `saved` with the id. `memory_forget` is a `delete`: `forgotten`. A failed check is an error result with its text. `trigger` is `tool`.
- **Other sessions.** After a change, every other open session, of any agent sharing this extension, that sees a memory the batch touched, before or after it, gets an announcement (`runtime.md` §5.1) with source `memory`: `changed` with its own memories as `loaded` lists them.
- **Consolidation** (with a store; at `pre_compact` by default, at `session_end` when configured, and whenever the host asks for it on an open session), for a session that is neither a task's child session nor a side chat, and only when its current context holds a human input. `session_end` runs it in an async hook named `memory`, `pre_compact` in a sync one, each for up to 60 s; the one at `session_end` is also bounded by the session's close timeout. `trigger` is `session_end`, `pre_compact`, or `host` for the host's. A store that implements the ingester interface gets the current context without its system line and epoch head, and what it reports is published as `memory.saved`. Otherwise one side request in bucket `memory`, with the history and no tools and at most 2048 output tokens, sends `consolidate` as a reminder with source `memory`: `{{user}}` and `{{project}}` the scope's, `{{memories}}` as `loaded` lists them, `{{user_used}}` and `{{shared_used}}` the two sums, `{{user_limit}}` and `{{shared_limit}}` the limits, and `{{user_words}}` and `{{shared_words}}` three quarters of each limit. The reply's text from its first `{` to its last `}` is a JSON object whose `changes` is the batch; a reply that does not parse, or a batch that fails its check, fails the hook.
