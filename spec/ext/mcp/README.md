# ext/mcp

A client for Model Context Protocol servers (protocol 2026-07-28, negotiating down as servers require). It offers their tools to the model, lists the servers in a catalog section, switches to discovery when the definitions grow large, and can offer each server's prompts as slash commands. The discovery tools are defined in `tools.json`; every other text the model sees is a section of `texts.md`, rendered by the template language of `runtime.md` §7. It is the one extension whose Go binding uses a third-party library, the official MCP Go SDK.

- **Servers.** A server has a name the host gives it, `^[A-Za-z0-9_-]{1,64}$`, unique in one install. The case is kept, so a name reaches tool names as the host wrote it. A name may contain `__`, but a prefix pattern over tool names then reaches another server's tools too: `mcp__a__*` also matches the tools of a server named `a__b`, and keeping such names apart is the host's part. The server's own `serverInfo.name` is never used. Each server is reached either by a command over stdio, whose credentials come from its environment, or by a URL over Streamable HTTP, with optional static headers on every request and optional OAuth. Installed for an agent, the connections serve all its sessions; installed for a session, they serve that session and close when it ends. Install connects every server at once and waits at most the connect timeout (30 s) for each first attempt. A server still down is retried in the background, from 1 s doubling to 5 min. Its tools are registered once it answers, taking effect at the next turn as any registration does. A connection offers the newest protocol version first, through `server/discover`, unless the host names an older version the SDK supports for that server; then it goes straight to `initialize`, for servers that mishandle `server/discover`.
- **Tools.** Every page of `tools/list` is read. A tool is skipped, with a warning, when its input schema is not an object schema, or when it is outside the server's allow list or on its deny list. Tools whose `x-mcp-header` is invalid are excluded by the SDK. The name the model uses is `mcp__<server>__<tool>`, with every character outside `[a-zA-Z0-9_-]` replaced by `_`. A name over 64 characters keeps its first 57, then `_` and the first 6 hex digits of the SHA-256 of the tool's own name. A second tool under a taken name is skipped. The description is the tool's title, if any, on its own line, then its description, both sanitized as foreign (`runtime.md` §13.7). The input schema is passed through, not strict. A tool runs in parallel only when the host trusts the server and the tool's `readOnlyHint` is true; otherwise it is serial. The list is read again on `notifications/tools/list_changed` and when its `ttlMs` runs out. Added tools are registered, removed ones unregistered, and a changed definition is announced as a registry update. A server that disconnects keeps its tools; calls to them fail until it reconnects.
- **Calls.** The arguments go to `tools/call` as given (`{}` when empty), with the call id as the progress token. Progress notifications become the call's progress, with the data `{progress, total}`. Canceling the call cancels the request. The kinds of failure:
  - A request that reaches no server: the result is `unavailable`, and the connection is dropped and reconnected.
  - A server waiting for the user to sign in, or past the retry bound: `sign_in`.
  - Any other protocol error: `server_error`, `{{kind}}` one of `invalid request` (-32602), `unknown tool` (-32601), `timed out` and `server error`. The server's error text never reaches the model or the events.
- **Results.** Content items for the user alone (an `audience` without `assistant`) are dropped.
  - Text becomes a text block, and an image an image block.
  - Audio becomes `audio_omitted`.
  - A resource link becomes `resource_link`, followed by ` (<mime>)` when it has one and its description on a new line.
  - An embedded resource with text becomes a text block. One with an image blob becomes an image block, and one with a PDF blob a document block named by its URI's last segment. Any other blob becomes `blob_omitted`.
  - `structuredContent` is checked against the tool's output schema, when it has one and the result is not an error; a mismatch makes the whole result `bad_output`. Otherwise it is the result's structured data, and, when no content block is left, its JSON is the text.
  - `isError` carries over.
  - An image block whose type is not `image/png`, `image/jpeg`, `image/gif` or `image/webp` (any letter case) becomes `media_unsupported`; an image or document block larger than the media limit (5 MiB of decoded bytes by default) becomes `media_too_large`. An API refuses such a block, and once committed it would fail every later request.
  - Text over the limit (50 000 characters in all) is cut and followed by `truncated`.
- **Catalog** (catalog slot, rendered at the start of an epoch). It is named `mcp` for an agent install and `mcp_session` for a session install, so the two stand side by side.
  - The section is left out when no server has been listed. Each server is a `server_open` … `server_close` item, in configuration order. It holds `server_instructions` when the server gave instructions, cut to 2000 characters after sanitizing; in discovery mode, it also holds `server_tools`, with one `tool_item` per tool (`{{summary}}` the description's first line, or the title, cut to 120 characters) or `tool_name_item` when there is no summary.
  - The install is in discovery mode for this epoch when none of its own tools is among the epoch's frozen tools and `mcp_call_tool` is. Then the section is `catalog_search`. It is in native mode when its frozen tools are deferred; then the section is `catalog_native`, with every server's item, instructions or not, and no `server_tools`. Otherwise it is `catalog`, which leaves out servers without instructions and is itself left out when none remains.
  - In discovery mode, while the section's length / 4 exceeds 5% of the context window, the servers with the most tools, one by one, list their tools by name only.
- **Changes inside an epoch** are announced as reminders that do not wake, with source `mcp`:
  - A new server: `connected` and its item, plus `connected_next_turn` in direct mode.
  - A connection lost: `disconnected`.
  - A server back after a loss: `reconnected`.
  - In discovery mode, a changed list: `tools_changed`, then `tools_added` with one `tool_item` per new tool, and `tools_removed` with the names joined by `, `.
  - A switch of mode: `mode_search` followed by every tool's `tool_item`, `mode_native`, or `mode_direct`.
- **Discovery.**
  - **Modes.** `direct` registers each tool; `search` registers only `mcp_search_tools` (parallel) and `mcp_call_tool` (serial); `native` registers each tool as deferred and one hosted tool, the neutral `tool_search` (`runtime.md` §4.6), so the provider searches the definitions and loads what it finds. A request to a model that cannot use the tool search sends the deferred tools as ordinary ones, as `direct` would. The default mode, `auto`, estimates the definitions as their JSON length / 4. It switches to `search` above 2% of the context window, or to `native` when the host asks for it, and back to `direct` below 1%. The window is the session's at session scope, and a configured one (200 000) at agent scope. The mode is decided again whenever the tool list changes.
  - **`mcp_search_tools`.** Its `servers` enum lists the servers. It needs `names`, `query` or both, else it answers `need_query`. Names are looked up exactly; one not found adds `unknown_tool`. The query matches each lower-cased word against the name (3 points), the title (2) and the description (1). It returns at most 20 tools by score, then by name; with none it adds `no_matches`. A host may replace the search.
  - **Search output.** The tools are grouped by server, each group under `search_server`, at the requested detail:
    - `names`: one `tool_name_item` per tool.
    - `descriptions`: the name, then its description on the next line.
    - `schemas`: one JSON object per tool, `{name, description, input_schema}`.

    The default detail is `schemas` when names were given, `descriptions` otherwise.
  - **`mcp_call_tool`.** It answers `unknown_tool` for a name it cannot find. It checks the arguments against the tool's input schema and answers `bad_arguments` when they do not fit. Otherwise it calls the tool as above. The discovery tools of a session install also reach the tools of its agent's install.
- **Approval.** The extension adds no review of its own: server tools follow the host's rules and hooks like any tool. In native mode the model calls each tool by its own name, so rules and hooks apply as in direct mode. Hosts pass their rules to the extension. It keeps every rule as given, and gives each rule whose `tool` starts with `mcp__`, `*` or `?` a twin:
  - id `<id>.via_call_tool`, tool `mcp_call_tool`, the same action and reason;
  - `when` holds `name` as a glob of the original `tool`, plus every original condition under `arguments.`;
  - a programmatic matcher, where the binding offers one, is applied to the call rewritten as the named tool and its arguments.
- **Prompts.** Only for a server the host enables. Every page of `prompts/list` is read when the server declares prompts, and read again on `notifications/prompts/list_changed` and when its `ttlMs` runs out. Each prompt is a command, registered where the install is:
  - Named `mcp__<server>__<prompt>` with both parts lower-cased, every character outside `[a-z0-9_-]` replaced by `_`, cut and hashed past 64 as tool names are. A name already taken is skipped with a warning.
  - Its description is the prompt's title, or the first line of its description, cut to 120 characters; its argument hint lists the arguments in order, `<name>` when required and `[name]` when not. It waits for the session to be idle, like any command by default.
  - A changed prompt is registered again; a removed one is unregistered; a server that disconnects keeps its commands, which then fail. Commands are never announced to the model, since only people invoke them.
  - **Running one.** The arguments are split into words as `runtime.md` §6 splits a command's, and given to the prompt's arguments in order; words beyond the last argument join it, separated by spaces. A missing required argument fails the command with its usage, and nothing reaches the model. `prompts/get` runs under the server's call timeout, a minute when it sets none; a server error fails the command, and an input request the server makes on the way is declined, since no call is there to route it to.
  - **The input.** One user message is sent as it is. Several messages, or any assistant message, become one input: each message, in order, after `prompt_user` or `prompt_assistant` on its own line, the messages separated by a blank line. Content converts as tool results do; text goes into the input's text, which the runtime escapes like any input, and images and documents follow it as parts. Text over the limit is cut and followed by `truncated`. The input goes in with origin `command`.
- **Credentials.** HTTP servers can take static headers, a host HTTP client, or OAuth 2.1 by the MCP authorization spec.
  - **What the SDK does:** resource metadata and authorization server discovery, client registration (client ID metadata document, then a pre-registered client, then dynamic registration, which is off unless asked for), PKCE, the `resource` parameter, the `iss` check, and scope step-up.
  - **Discovery, registration and token requests** go through a client that allows only https and refuses, at dial time, loopback, private, link-local, CGNAT, multicast and unspecified addresses, redirects included. A development switch lifts this, and a host client can replace it.
  - **Signing in.** An authorization URL is handed to the host only when it is https, or http when the development switch is on. When it is, `mcp.auth_required{server, state: "waiting", auth_url}` is published, and the host's authorize function returns the code, state and `iss` from the redirect.
    - For servers, the callback authorizer is mounted at the redirect URL. It matches the redirect by `state`, uses each state once, and waits 10 minutes.
    - For desktops, the loopback authorizer listens on a free 127.0.0.1 port and opens the system browser without a shell.
  - **Retry bound.** After 3 failed authorizations in a row the server stops trying, and `mcp.auth_required{state: "failed"}` is published.
  - **Token store.** Grants `{token, token_url, client_id, client_secret}` go to the host's token store whenever a new access token is issued. A stored grant with a refresh token is refreshed after a restart without asking the user.
  - Tokens, codes and header values never appear in logs, events, errors or the model's context.
- **Elicitation.** The client declares form and URL elicitation.
  - A server's request is routed to the call it belongs to. That is the call's own context under multi round-trip requests; otherwise it is the connection's only call in flight, and with none or several the request is declined.
  - A URL request whose URL is not https is declined.
  - `mcp_elicitation` (keyed on the server, 10 minutes, closed: a failure declines; sync only) fires in that call's session. It takes `{server, tool, mode, message, requested_schema, url}` with the hook environment and answers `{action, content}`; the first answer with an action ends the chain. No hook, or an action other than `accept` or `cancel`, declines.
  - The content goes back to the server only. `mcp.elicitation{server, tool, mode, action}` is published.
- **Events.**
  - `mcp.server_status{server, state, tools, error}` on every change of state: `connecting`, `ready`, `failed` or `closed`. `error` names only the kind.
  - `mcp.auth_required` and `mcp.elicitation`, as above.
  - An agent install publishes on every open session of the agent, a session install on its session.
