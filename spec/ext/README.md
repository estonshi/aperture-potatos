# Extension data

Each extension that ships model-visible text or data keeps it under `ext/<extension>/`, so deleting the extension deletes its data too. Like every other file here, these texts are byte-for-byte the same in every binding. Every text with placeholders is a template in the language of `runtime.md` §7: a value goes in verbatim and is never expanded again, and an unknown placeholder renders empty.

An extension with events or hook points describes them in `events.schema.json` and `hooks.schema.json`. The events schema checks the kernel envelope (`schema/event.schema.json`) and attaches each of its payloads by `type`, under the `$defs` key that is the type with `.` written `_`. The hooks schema has `<point>_input`, which carries the kernel hook environment (`schema/hook.schema.json#/$defs/env`), and `<point>_output`. Their examples sit in `examples/<valid|invalid>/<events|hooks>/<target>.<case>.json`, named and checked as under `schema/examples`.

An extension's loop conformance cases live in `conformance/loop/ext/<extension>/`. A case names the extensions it loads in `agent.extensions`, name → options, and uses only the kernel's actions; `conformance.md` lists the options, their defaults and how any test double behaves, so every binding builds the same instance. The command extensions have no directory here: they are named `cmd.clear`, `cmd.compact`, `cmd.context`, `cmd.fork`, `cmd.help`, `cmd.rewind` and `cmd.usage`; `cmd.clear` and `cmd.rewind` take `interrupt` (interrupt the running turn instead of waiting for it to end), the others take no options, and every current case passes `{}`.
