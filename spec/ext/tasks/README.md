# ext/tasks

The model's four tools over the task manager (`runtime.md` §13), a capabilities section, and the list of unfinished tasks after compaction. The tool definitions are `tools.json`; every text the model sees is in `results.md` or `guidance.md`, sent byte for byte. Each tool calls the manager with its call's context, so the task is recorded against the call's result line, and a stop or restart the model asked for sends no notification.

- **Errors.** A task id the manager does not know gives `not_found`; a send to a running task whose kind takes no instructions `no_instructions`; a send to a finished task whose kind cannot continue `not_continuable`; a restart of a kind that cannot restart `not_restartable`; a restart or continuation while another holds the task `busy`; a send to a full inbox `queue_full`. Every other failure of a start, restart or continuation (the task limit, a `task_start` refusal, a restart the gate refused, a constructor error) is the runtime's own text (`prompts/reminders.md`: `task_limit`, `task_not_started` or the gate's text, `task_start_failed`). All of them are error results.
- **`task_status`** (parallel). With `task_id`, a positive `wait_ms` (at most 600,000) first waits, bounded by the call, for the task to end or ask for input. It then inspects the task (`runtime.md` §13.3), for at most 10 seconds; a failed inspection reports the last progress. The result is one text block, a JSON object with, in this order, `task_id`, `kind`, `title`, `status`, `attempt`, `started_at`, then only when set `ended_at`, `progress` (`text`, `percent`; never its data), `question`, `error`, `abandoned`, `pending_instructions`, and `summary` for a finished task. With `include_result: true` a finished task's result content follows as further blocks, its text sanitized as foreign text (`runtime.md` §13.7). Without `task_id` the object is `{"tasks": [...]}`, each task's `task_id`, `kind`, `title`, `status` and `attempt` in the order the tasks were created; `wait_ms` and `include_result` do nothing then.
- **`task_send`** (serial). The instruction is `message` in `mode` (`next_loop` by default; another value is invalid input). A running task gets `delivered` with the mode; a finished task that continues gets `continuing` with the new attempt.
- **`task_stop`** (serial). A finished task gives `already_finished` with its status. Otherwise the tool asks the manager to stop it and then checks every 50 ms, bounded by the call, until the attempt it stopped has ended or been replaced: `stopped`, or `abandoned` when the manager gave the attempt up after the grace period.
- **`task_restart`** (serial, not strict). `input` is the new input, in the shape the task was started with; a `tool_exec` task takes the wrapped tool's own input. The result is `restarted` with the new attempt's number, one more than the task's attempt before the call; the new attempt runs in the background.
- **Capabilities section** `guidance.md`, rendered only when one of the four tools is in the frozen tool set.
- **After compaction** a `post_compact` hook adds, when some task is unfinished, `unfinished` followed by one line per unfinished task in creation order, at most 50: `- <task_id> <kind> "<title>": <status>`.
